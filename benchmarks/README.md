# Benchmark suite

Сравнение `spa-toolkit` с React, Vue, Svelte и Solid по одному и тому же
набору сценариев (создание/обновление/удаление строк, большая форма, большая
таблица, навигация, монтирование компонентов, bundle size, память). Методика
и точный контракт — [SPEC.md](./SPEC.md). Классическая часть (create/update/
select/swap/remove на таблице строк) дословно повторяет разметку
[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark).

## Структура

```
benchmarks/
  SPEC.md      — контракт: маршруты, id-элементов, семантика каждого сценария
  harness/     — Playwright-раннер, одинаково водит любое из приложений ниже
  apps/        — по одному приложению на фреймворк (spa-toolkit/react/vue/svelte/solid)
  results/     — *.json на фреймворк + сводный REPORT.md (генерируются, не пишутся руками)
```

## Установка (один раз)

```sh
cd C:\Myin\_КОД\spa-toolkit
pnpm install
```

## Прогнать один фреймворк

```sh
cd benchmarks/harness
npx tsx src/runner.ts spa-toolkit
```

Вместо `spa-toolkit` — `react` / `vue` / `svelte` / `solid` (любая папка из
`benchmarks/apps/*`). Скрипт сам:

1. соберёт приложение (`vite build`);
2. поднимет `vite preview` на порту 4173;
3. прогонит headless Chromium через все ~17 сценариев из
   [scenarios.ts](harness/src/scenarios.ts);
4. измерит bundle size и heap после нескольких циклов create/clear;
5. запишет `benchmarks/results/<framework>.json`.

Занимает **5-10 минут на один фреймворк** — это нормально, не зависание:
много сценариев гоняются по 5-8 раз каждый (для медианы), и часть повторов —
это полные перезагрузки страницы, а не лёгкие клики.

### Несколько проходов для усреднения

```sh
npx tsx src/runner.ts spa-toolkit 3
```

Второй аргумент — число полных проходов; сэмплы всех проходов объединяются
в одну медиану на сценарий. ⚠️ Время растёт **пропорционально числу
проходов** — 3 прохода одного фреймворка может занять 20-40+ минут в
зависимости от машины. На не самой свежей машине это может быть непрактично
для всех 5 фреймворков сразу — см. следующий раздел.

## Прогнать все фреймворки одной командой

```sh
npx tsx src/runAll.ts
# или через npm-скрипт:
npm run bench:all
```

Сам находит все папки в `benchmarks/apps/*` и прогоняет их **по очереди**
(не параллельно — так надёжнее, см. ниже), затем сам генерирует сводный
отчёт. Необязательный аргумент — число проходов на каждый фреймворк:

```sh
npx tsx src/runAll.ts 3
```

Реалистичная оценка времени: 5 фреймворков × 5-10 минут ≈ **30-60 минут**
на один проход каждого. С `passes=3` это уже часы — сначала попробуйте без
аргумента (по одному проходу на фреймворк), этого обычно достаточно.

## Собрать сравнительную таблицу без нового прогона

```sh
npx tsx src/report.ts
```

Читает всё, что уже лежит в `benchmarks/results/*.json`, и печатает/сохраняет
`benchmarks/results/REPORT.md`. Не обязательно гонять все 5 фреймворков —
работает с тем подмножеством, что уже есть на диске.

## Если что-то пошло не так

**Порт 4173 занят** (обычно — после прерванного прогона):

```sh
netstat -ano | findstr :4173
taskkill /F /PID <тот PID>
```

**Прогон подозрительно медленный** (в разы медленнее, чем в этом README) —
скорее всего накопились зомби-процессы `node.exe` от прошлых прерванных
прогонов. Проверить и почистить:

```sh
tasklist /FI "IMAGENAME eq node.exe"
taskkill /F /IM node.exe   # убьёт ВСЕ node.exe — сначала закройте то, что не хотите терять
```

**`create-100k` упал с "Target crashed"** — headless Chromium иногда не
выдерживает 100 000 строк (400k+ DOM-узлов). Это легитимный, ожидаемый
результат на некоторых машинах/фреймворках, не баг harness'а — раннер сам
восстанавливает браузер и продолжает со следующего сценария (см. комментарии
в [runner.ts](harness/src/runner.ts) про изоляцию страниц/браузера).

## Известное ограничение методологии

`performance.memory.usedJSHeapSize` в headless Chromium квантуется (защита
от fingerprinting) — в наблюдавшихся прогонах эта метрика выходила
**идентичной у всех фреймворков**, что не похоже на реальный сигнал. Не
доверяйте строкам "Heap after..." в отчёте без независимой перепроверки
(например через CDP `HeapProfiler` heap snapshot вместо `performance.memory`).
