# Benchmark app contract

Каждое приложение в `benchmarks/apps/<framework>` реализует **один и тот же**
набор сценариев с **одинаковой разметкой (`id`-контракт ниже)**, чтобы
`benchmarks/harness` могло управлять любым из них одинаковым кодом через
Playwright и получать сравнимые числа. Не меняйте `id` — harness ищет элементы
именно по ним, а не по тексту/классам.

Классическая часть (create/update/select/swap/remove на таблице строк)
дословно повторяет разметку и семантику
[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark)
(`#run`, `#runlots`, `#add`, `#update`, `#clear`, `#swaprows`, клик по строке,
клик по кнопке remove в строке) — это позволяет при желании сверить числа с
публичными таблицами того проекта. Остальные сценарии (100k, 1000 updates,
1000 components, large form, large table, route navigation) — расширение
поверх этого, специфичное для данного сравнения.

## Технические требования к приложению

- Vite + TypeScript, собирается в `dist/` через `vite build` (`npm run build`
  / `pnpm build` внутри пакета).
- `npm run dev` / `pnpm dev` поднимает dev-сервер для локальной проверки
  (harness гоняет тесты против **production build + preview server**, не
  против dev-сервера — важно для честных чисел, dev-сборки framework'ов
  обычно заметно медленнее).
- `package.json.name` — `@bench/<framework>` (например `@bench/react`).
- Никакого лишнего в бандле: без роутинг-библиотек там, где не нужны для
  сценария "route navigation" (эта библиотека — единственное разрешённое
  исключение, и то только на странице `/route-navigation`, см. ниже).
- Каждая "страница"/раздел сценария реализуется как отдельный route
  (см. таблицу маршрутов), а не переключением видимости div'ов — так честнее
  меряется code-splitting/lazy loading там, где framework это поддерживает
  (если framework не поддерживает лёгкий client routing "из коробки" —
  используйте его стандартный роутер: `react-router`, `vue-router`,
  `svelte-spa-router` или `svelte`'s own, `@solidjs/router`).

## Маршруты

| Путь | Сценарий |
|---|---|
| `/` | Стартовая — пустая, только чтобы замерить **initial render** (см. ниже) |
| `/table` | Классическая таблица (js-framework-benchmark: run/runlots/add/update/clear/swap/select/remove) |
| `/table-100k` | То же самое, но с кнопкой на 100k строк (`#run100k`) |
| `/updates-1000` | Сценарий "1000 обновлений" |
| `/components-1000` | Сценарий "1000 компонентов" |
| `/large-form` | Форма на 200 полей |
| `/large-table` | Табличный грид на 10k строк с сортировкой/фильтром |
| `/route-a`, `/route-b` | Две "полновесных" страницы для сценария route navigation |

## Сценарии и `id`-контракт

### 1. Initial render (`/`)

Пустая страница-обёртка приложения (шапка/layout, если он у вас есть, без
данных). Harness меряет `navigation start → load event` и, отдельно,
`domInteractive`. Единственное требование: на странице должен быть элемент
`#app-ready`, который появляется **после** гидратации/маунта корневого
компонента (не в статичном `index.html`) — это и есть "готово к
взаимодействию".

### 2. Классическая таблица (`/table`)

Таблица `id="table"` строк `<tr>` с (как минимум) двумя `<td>`: id и label
(label — ссылка `<a>`, по клику на которую строка выделяется). Кнопки:

- `#run` — заменить содержимое 1 000 строками (`create 1,000 rows`).
- `#runlots` — заменить содержимое 10 000 строками (`create 10,000 rows`).
- `#add` — добавить 1 000 строк к уже отображённым.
- `#update` — обновить label каждой **10-й** строки (дописать `" !!!"`).
- `#clear` — очистить таблицу.
- `#swaprows` — поменять местами 2-ю и предпоследнюю (index 998 при 1000
  строках) строки.
- Клик по `<a>` внутри строки — выделить строку (класс `danger` на `<tr>`,
  снять с предыдущей выделенной).
- Клик по кнопке remove в строке (`<a><span class="glyphicon glyphicon-remove">`
  или любой элемент с `data-action="remove"` внутри `<td>` строки) — удалить
  эту строку.

Точная семантика (id генерируются инкрементально и не переиспользуются между
`run`/`runlots`, `label = "<adjective> <colour> <noun>"` из фиксированных
списков слов — как в оригинальном benchmark'е, это не принципиально для
честности сравнения, но упрощает визуальную проверку) — см. референс-реализацию
`benchmarks/apps/spa-toolkit` после её появления, либо оригинальный
`js-framework-benchmark` (frameworks/keyed/vanillajs/src/main.js) как образец.

### 3. 100k строк (`/table-100k`)

Та же таблица, плюс кнопка `#run100k` — создать 100 000 строк. Не обязано
поддерживать update/swap/select/remove на таком объёме (но можно, если не
жалко) — harness меряет только время самого `#run100k`.

### 4. 1000 обновлений (`/updates-1000`)

На странице должен быть элемент `#app-ready` (harness ждёт именно его перед
тем, как нажать кнопку — та же семантика, что на `/`, см. п.1).

Таблица/список из 1 000 строк, отрендеренных один раз при заходе на страницу.
Кнопка `#update-1000-sequential` — по клику framework должен выполнить
**1 000 последовательных точечных обновлений** (не один batched re-render):
цикл `for i in 0..999: row[i].label = row[i].label + "*"`. Смысл сценария —
измерить стоимость мелкогранулярных точечных мутаций, а не стоимость одного
большого re-render. Если framework обычно батчит апдейты (React) — не
оборачивайте цикл в `startTransition`/`flushSync`-трюки, пусть ведёт себя как
обычный код разработчика; harness должен увидеть реальное поведение "из
коробки".

### 5. 1000 компонентов (`/components-1000`)

На странице должен быть элемент `#app-ready` (та же семантика, что на `/`).

Кнопка `#mount-1000` — смонтировать 1 000 экземпляров **не тривиального**
компонента (не `<li>`, а компонент с собственным локальным состоянием):
карточка задачи с чекбоксом (локальный `checked: boolean` state), текстом и
кнопкой-счётчиком (клик увеличивает локальный счётчик именно этого
экземпляра, не общий). Компонент должен быть определён так же, как вы бы
определили его в реальном приложении на этом framework'е (со всеми его
обычными накладными расходами — hooks/reactivity/lifecycle), не
оптимизирован вручную под тест. Кнопка `#unmount-1000` — размонтировать всё
(для последующего сценария memory).

### 6. Большая форма (`/large-form`)

Форма `id="large-form"` из **200 полей**: смесь `text`/`number`/`checkbox`/
`select` (пропорция на ваше усмотрение, но не меньше 30 text и не меньше 20
checkbox). Кнопка `#fill-form` — программно выставить значения во все 200
полей (эмулирует "вставили из буфера"/"подставили дефолты"), это и есть
измеряемая операция. Если framework делает валидацию по изменению — она
должна быть подключена как в реальном приложении (не выключена ради теста).

### 7. Большая таблица (`/large-table`)

Грид `id="big-table"` на **10 000 строк**, минимум 5 колонок (id, name,
email, status, дата). Загружается сразу при заходе на страницу (harness
меряет **initial render** этой страницы отдельно от `/table`, т.к. тут
колонок больше — это про "реальный тяжёлый грид", а не про синтетику).
Кнопки:
- `#big-table-sort` — отсортировать по колонке `name` (уже отрисованные 10k
  строк переупорядочиваются, не пересоздаются с нуля, если framework это
  умеет естественным образом).
- `#big-table-filter` — отфильтровать по подстроке в `name` (захардкоженная
  строка в вашем коде, дающая ~10% совпадений), затем `#big-table-clear-filter`
  возвращает все строки.

### 8. Route navigation (`/route-a`, `/route-b`)

Обе страницы — не заглушки: каждая рендерит таблицу из 200 строк (своя
разметка, не переиспользование `/table`) плюс пару других элементов, чтобы
переход между ними был сопоставим с реальной SPA-навигацией, а не пустым
экраном. `#nav-to-b` на `/route-a` — SPA-переход (не полная перезагр;
`pushState`/router-эквивалент) на `/route-b`, `#nav-to-a` на `/route-b` —
обратно. Элемент `#route-ready` появляется на каждой из двух страниц после
монтирования её содержимого (аналог `#app-ready`, но per-route — для замера
именно длительности перехода, не только его старта).

## Что НЕ надо делать

- Не оптимизируйте реализацию под тест сильнее, чем сделал бы обычный
  разработчик этого framework'а (никаких `memo` на каждый чих ради красивых
  цифр, если типичный код так не пишут) — цель сравнения честная, а не
  "у кого читерство изощрённее".
- Не добавляйте сторонние UI-кит/CSS-фреймворки (Tailwind и т.п. — можно
  голый CSS, но не тяните лишний JS в бандл ради стилей).
- Не мокайте/не убирайте реальную работу framework'а (виртуальный DOM/diff/
  reactivity graph) — измеряем именно её стоимость.

## Как проверить локально перед сдачей

```sh
pnpm --filter @bench/<framework> build
pnpm --filter @bench/<framework> preview   # или свой скрипт preview
```

Открыть каждый маршрут руками, нажать все кнопки, убедиться что ничего не
падает в консоли и визуально таблицы/формы ведут себя ожидаемо (строки
реально появляются/пропадают/сортируются). Harness запускается из
`benchmarks/harness` (`pnpm --filter @bench/harness run bench -- <framework>`)
и не прощает падений/таймаутов молча — если сценарий не работает, число
просто не попадёт в отчёт для этого framework'а.
